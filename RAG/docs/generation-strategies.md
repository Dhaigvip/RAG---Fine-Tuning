# Generation Strategies — Reference

## Problem statement
Retrieval now works and is measured (Hit Rate 0.909, MRR 0.909 — see `evaluation-strategies.md`), but nothing in this project has ever turned a retrieved chunk into an answer a person actually reads. `step04_hybrid_search.py`'s `search()` returns `(parent_id, score)` pairs and stops there. Two distinct risks sit directly ahead of that, and they are NOT the same risk:

1. **Ungrounded answers.** A generative LLM asked "answer this question" will answer it — from its own training knowledge if it has to — even when the notes handed to it don't actually cover the question. That defeats the entire point of RAG over personal notes: the value of grounding to *this specific corpus* (over just asking the model directly) is that the answer is traceable to something real and checkable. An LLM that quietly fills gaps from general knowledge produces an answer that LOOKS grounded but isn't, which is worse than an answer that's visibly unsupported.
2. **No way to check a wrong answer.** Even when the LLM does stick to the provided context, a plain prose answer with no reference back to which chunk it came from gives no way to verify it against the source note without re-reading everything.

There's also a concrete reason not to treat "a chunk was retrieved" as "the question is answerable": `search()` already has a MISS case in real, measured data — the `docker-02` retrieval-eval question never got its correct source back at all. A MISS doesn't necessarily mean `search()` returned nothing (`FINAL_TOP_K=3` keeps filling from whatever passed the relevance threshold, right or wrong) — it means the CORRECT chunk wasn't among what came back. If generation is built with no defense against this, that's exactly the scenario where an LLM would receive plausible-but-wrong context and, being generative, would very likely still produce a fluent, confident answer with nothing in the output telling the user retrieval had actually failed for that question. Generation has to defend against this structurally — a prompt that just says "be helpful" won't catch it, because the model has no way to know from inside the prompt whether the context it was handed is actually sufficient versus merely topically adjacent.

## Solution
Build a small generation layer on top of the existing `search()`: retrieve, hand the promoted parent chunks to an LLM as clearly numbered, bounded context, instruct it to answer ONLY from that context and to say so explicitly when it can't, and require it to cite which numbered source(s) it drew from. Validate the citations programmatically after the fact (do the cited numbers actually exist in the source list?) rather than trusting the model's citation behavior blindly — the same "flag, don't just hope" pattern already used for the rerank relevance threshold and HyDE's fallback.

Two independent refusal mechanisms, not one:
- **Retrieval-level (hard, free):** `search()` already returns `[]` when nothing passes the relevance threshold — reuse that signal to skip generation entirely and refuse before spending an LLM call. This is a pre-existing, already-verified signal; there's nothing new to build here beyond wiring it up.
- **Generation-level (soft, prompted):** even when `search()` DOES return chunks, that only means something was *topically relevant enough to pass reranking* — not that it actually *answers this specific question* (the `docker-02` MISS shows retrieval can return the wrong thing with total confidence). The prompt explicitly instructs the model to say a fixed, detectable refusal phrase when the provided context doesn't actually answer the question, so refusal is checkable in code (substring match) rather than something only a human reading the output would notice.

## Landscape of grounding & citation approaches

**Plain prose + inline bracket citations `[1]`, `[2]` — chosen for this pass.** Sources are numbered in the prompt in the same order `search()` already ranks them; the model is instructed to cite the bracket number(s) it drew from inline, next to the relevant part of its answer. Simple, human-readable directly (no rendering step needed), and cheap to validate: after generation, regex out every `[n]` in the answer text and check each `n` is actually within `1..len(sources)` — catches a fabricated or out-of-range citation number, a real failure mode worth catching cheaply even though it says nothing about whether the CONTENT near that citation is actually faithful to the source (that's the harder faithfulness question, deferred below).

**Structured JSON output (`{"answer": ..., "citations": [1, 3]}`) — considered, deferred.** More reliable to parse than regex (no ambiguity between a citation and, say, literal bracketed text the model happens to generate), but requires the model to reliably produce valid JSON on every call, adds a parse-and-retry-on-malformed-JSON path, and couples the citation format to a stricter contract than this pass needs. Worth adopting if inline-bracket parsing turns out fragile in practice against real generated output — that's an empirical question this project's "verify against real data, not assumptions" habit will actually answer once `step05_generate.py` has real runs behind it, not something to guess at up front.

**Forced tool-use / function-calling schema for citations — considered, deferred.** Bedrock supports Claude tool-use, which could force a schema-compliant citation object per claim — the most robust option technically, but a materially bigger lift (tool schemas, structured extraction, multi-turn tool-result handling) for what this project's Sept 15-16 scope is: understanding grounded generation and refusal, not building a production citation-verification pipeline. Revisit if JSON output (above) also proves too fragile.

## Landscape of refusal approaches

**Retrieval-level short-circuit on empty `search()` results — chosen, already free.** No new logic: `promoted == []` already means nothing passed the relevance threshold, so skip the generation call outright and return the refusal directly. Costs nothing extra (no LLM call at all for this case) and reuses a signal that's already been verified correct by the retrieval eval harness.

**Prompted refusal phrase, detected by substring match — chosen, the main new piece.** The system prompt instructs the model to respond with an exact, fixed phrase when the retrieved context doesn't answer the question, even when chunks WERE retrieved. Detecting that phrase in the output (case-insensitive substring) gives a cheap, checkable `refused: True/False` flag without needing a second model call. The known weakness: this is a soft instruction, not a guarantee — the model can still ignore it and hallucinate confidently instead of refusing. Nothing catches that failure mode in this design; see the next option.

**Post-hoc faithfulness check via a judge LLM (RAGAS-style) — considered, deferred, same reasoning as `evaluation-strategies.md`.** This is the actual hard guarantee: a second model call that checks whether the generated answer's claims are actually supported by the retrieved context, independent of whether the FIRST model chose to self-report insufficiency. `evaluation-strategies.md` already deferred RAGAS's faithfulness metric for exactly this reason — no generation step existed yet to evaluate. Now one does, so this is the direct, concrete next step once `step05_generate.py` has real output to check — either via RAGAS/DeepEval or a hand-rolled Bedrock-judge call following the same pattern already used for HyDE generation. Explicitly not attempted in this pass: it needs real generated answers to design against, the same "don't build the eval before there's something real to evaluate" reasoning this project already applied once.

**Structured `sufficient_context: bool` field alongside the answer — considered, deferred, pairs naturally with the JSON-output option above.** More machine-checkable than parsing a magic phrase out of prose, but only worth the complexity if/when JSON structured output is adopted for citations anyway — no reason to add this alone while the answer itself stays plain prose.

## Chosen design
- **Model — separate config from HyDE, updated Sept 15 to Claude Haiku 4.5.** `TOOL_RAG_GENERATION_MODEL` (default `eu.anthropic.claude-haiku-4-5-20251001-v1:0`, matching `TOOL_RAG_HYDE_MODEL`'s default) — kept as its OWN env var rather than reusing `TOOL_RAG_HYDE_MODEL`, on purpose: HyDE's output is throwaway (never shown to a user, only used to improve an embedding), while generation's output IS the user-facing deliverable — quality matters more here, and a future upgrade to a stronger model for generation shouldn't silently also change what HyDE generates internally, even though both happen to point at the same model right now.
  - *Superseded reasoning, kept for the record*: this originally defaulted to `anthropic.claude-3-haiku-20240307-v1:0` — the one model confirmed directly invocable in `eu-central-1` with no cross-region inference profile, deliberately avoiding the extra IAM surface a `eu.`/`global.`-routed profile needs (see `query_transform.py`'s original model-choice note). An explicit standing instruction (Sept 15) now overrides that avoidance project-wide, accepting the inference-profile IAM surface in exchange for a stronger model.
  - **Confirmed working end-to-end (Sept 16)**: the real `/ask` API test (see Verification below and `docs/api-strategies.md`) called this exact model id through `call_generation_model()` and got back a correctly-grounded, correctly-cited answer — no `AccessDenied`/`ValidationException`. The `eu.`-routed inference profile is authorized for this account. (This confirms the profile generically and via generation specifically; it does not by itself confirm HyDE's own call to the same model id, since HyDE hasn't fired in any pasted run yet — see `query-transformation-strategies.md`.)
- **Retry on throttling, unlike HyDE.** `query_transform.py`'s `generate_hyde_document()` deliberately fails fast and falls back to the raw query on ANY error — a reasonable choice because HyDE has a safe fallback (embed the raw query instead). Generation has no equivalent fallback — it IS the output — so `step05_generate.py` follows `step02_embed.py`'s retry-with-backoff pattern on `ThrottlingException` instead of failing fast. Different failure philosophy, same reasoning already established in this codebase: fail fast only when there's something safe to fall back to.
- **Prompt shape:** a system-level instruction block (grounding rule, citation format, the exact refusal phrase) plus a user message containing the numbered sources (`source_file`, `header_path`, full parent `text`) followed by the actual question. Sources are numbered in `search()`'s existing rank order — no re-sorting.
- **Refusal, two layers, checked in order:**
  1. `search()` returns `[]` → return the refusal immediately, `reason: "no_retrieval"`, zero generation calls made.
  2. Otherwise, generate, then check the answer text for the exact refusal phrase (case-insensitive substring) → `refused: True, reason: "model_declined"` if found, `refused: False` otherwise. Both cases still return whatever sources were retrieved, so a refusal is inspectable (what WAS retrieved, that just didn't answer the question) rather than a bare "no" — useful for debugging retrieval gaps like `docker-02` later.
- **Citation validation, not enforcement:** after generation, extract every `[n]` from the answer text and check each against the actual number of sources provided. Out-of-range citations are surfaced as `invalid_citations` in the result (a flag for whoever's reading the output, human or a future eval script) — NOT auto-corrected or hidden, and not a hard failure that discards the answer. Same "surface it, don't silently paper over it" pattern as the rerank relevance threshold.
- **Pure functions kept separate from the AWS call**, mirroring every prior module in this project (`apply_min_score`, `reciprocal_rank_fusion`, `promote_to_parents` in `step04_hybrid_search.py`; `resolve_promoted`, `find_expected_rank` in `evaluate_retrieval.py`): `resolve_sources()` (promoted parent_ids → numbered source dicts), `build_prompt()` (sources + query → the actual prompt string), `parse_citations()` (answer text + source count → found/invalid citation numbers), `detect_refusal()` (answer text → bool). All four are unit-testable with zero AWS/FAISS involvement — see `tests/test_generate.py`.

## What's deferred
Faithfulness verification via a judge LLM (RAGAS-style or hand-rolled) — the real fix for the "model ignores the refusal instruction and hallucinates confidently anyway" gap that prompted-refusal alone cannot close; needs real generated answers to design against, which don't exist until this pass runs for real. Structured JSON/tool-use output for citations — plain bracket citations are the simpler starting point; revisit only if regex-based validation proves fragile against real output. A FastAPI endpoint wrapping this — the Sept 15-16 plan line mentions "assemble end-to-end pipeline (simple FastAPI endpoint)," but that's an interface around `step05_generate.py`'s logic, not the logic itself; sequenced AFTER `step05_generate.py` is verified working standalone (same "prove the piece works before wrapping an interface around it" order used for every other module so far — `step04_hybrid_search.py` was a CLI script long before anything considered wrapping it).

## Verification
Ran for real, two separate cases:

- **CLI (`python step05_generate.py "how do I clean up branches and stashes"`), Sept 15**: only a weak retrieval match came back (`note4-many-small.md`, low relevance — HyDE was off, `TOOL_RAG_QUERY_TRANSFORM` resolved to `none`), and it didn't actually cover the question — the model correctly produced the fixed refusal phrase rather than answering from general knowledge. This is the "MISS, model should refuse" case this design was built to handle.
- **API (`POST /ask`, same question), Sept 16** — see `docs/api-strategies.md`'s Verification section for the full real output: a *different*, more interesting case. The same weak match this time partially covered the question (branch deletion and `git stash pop` were both in the matched chunk). Rather than refusing outright or fabricating a general answer, the model answered only what the sources supported, cited `[1]` correctly, and explicitly flagged the part the sources didn't cover ("the sources don't provide a command to directly delete or clear stashes"). This is the partial-coverage boundary case — distinct from a clean hit and from a total miss — working as designed.

Both runs also confirm `eu.anthropic.claude-haiku-4-5-20251001-v1:0` works end-to-end for generation (see the Model choice note above).

Not yet run: a question with strong/clean retrieval coverage (an `exact`-difficulty question from `retrieval_eval_set.json`), to see the citation/grounding behavior on the easy case rather than only the miss and partial-coverage cases seen so far. Also not yet run: `docker-02` specifically through `step05_generate.py`, to see directly whether that known retrieval MISS produces a refusal or a hallucinated answer.
