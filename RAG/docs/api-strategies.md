# API / Deployment Strategies — Reference

## Problem statement
Every piece of this pipeline so far (`step04_hybrid_search.py`, `step05_generate.py`) only works as a one-shot Python CLI invocation — `python step05_generate.py "<question>"`. That's the right way to build and test each stage, but nothing else can call it: no frontend, no client app, not even a plain `curl` request. The Sept 15–16 plan explicitly calls for "assemble end-to-end pipeline (simple FastAPI endpoint)" — this closes that out, and it's directly interview-relevant too: "design an LLM-powered feature at scale" (Q5 in `interview-questions.md`) already assumes a request/response interface exists to design around.

## Solution
A minimal FastAPI app (`step06_api.py`) wrapping `step05_generate.py`'s `generate_answer()` behind one POST endpoint, plus a health check, Pydantic request/response validation, and explicit error handling so a Bedrock failure returns a clean HTTP error instead of an unhandled stack trace.

## Landscape

**FastAPI — chosen (already decided in the plan's own wording, but a reason is still worth stating).** Python-native, so no language/context switch from the rest of this project. Built-in Pydantic request/response validation and automatic interactive docs (`/docs`) for free — a request with the wrong shape gets a clean `422` before any application code runs. Async-capable if this project ever needs it. Flask is simpler but has no built-in validation or auto-docs (needs Flask-RESTX or hand-rolled validation); Django REST Framework is far more machinery than one endpoint needs. FastAPI is the standard fit for exactly this shape of project.

**Sync `def` endpoint, not `async def` — the actual interesting decision.** FastAPI supports both, and the choice genuinely matters here: an `async def` endpoint runs directly on the single-threaded event loop, so a BLOCKING call inside it — boto3's synchronous Bedrock calls, FAISS's synchronous C++ search — would freeze that event loop for every other concurrent request until it finishes. Nothing in this codebase (`boto3`, `faiss`, `sentence-transformers`) is async-native, and rewriting it to be async is real, unnecessary work for "a simple endpoint." Declaring the endpoint as plain `def` tells FastAPI to run it in a thread pool automatically — the correct way to expose synchronous, blocking code safely under an async framework without rewriting the blocking code itself. Worth naming directly in an interview: "how do you serve a blocking ML/AI pipeline behind an async web framework."

**Index/parents loaded per-request, not once at startup — flagged, deliberately deferred.** `step03_faiss_search.py`'s `load_index()` calls `faiss.read_index()` (a disk read) and re-parses the metadata JSONL on EVERY call; `step04_hybrid_search.py`'s `search()` also calls `load_parents()` (another JSONL parse) every call. Nothing is cached across calls today. At this project's 5-note corpus this costs milliseconds and is invisible — but at real scale, re-reading and re-parsing a FAISS index from disk on every single request is genuinely wasteful; the real fix is a one-time load in a FastAPI startup/lifespan hook, holding the loaded index/metadata in memory and reusing them across requests. Not done here — this endpoint deliberately leaves `step04_hybrid_search.py`/`step05_generate.py` completely unmodified (matches this project's habit of expanding the surface additively rather than reshuffling working code) — documented as a real, known gap rather than silently accepted. Worth naming directly in an interview as a concrete production-readiness gap, not waved away.

**One endpoint, not several.** `POST /ask` (question in, `generate_answer()`'s full result out) plus `GET /health`. A raw `POST /search` (retrieval only, no generation cost, useful for debugging) was considered — genuinely useful, but out of scope for "simple"; trivial to add later by wrapping `step04_hybrid_search.py`'s `search()` the same way.

**Error handling — catch and translate, don't let internals leak.** `generate_answer()`'s `call_generation_model()` raises after exhausting its retry budget (see `step05_generate.py`) on a real Bedrock outage/throttling situation — an uncaught exception in a FastAPI endpoint becomes an unstructured `500` with a raw stack trace by default. Caught and translated to a `503` (service temporarily unavailable — the honest status for "the downstream dependency is having a bad day") carrying only the exception TYPE name, not its message, so internal details (stack traces, potentially sensitive error text) never reach the caller. Deliberately coarse: any exception (a real Bedrock outage, or the index simply not being built yet) currently maps to the same `503` — fine for local dev, but doesn't distinguish a transient issue from a setup/config error; real production monitoring would want that distinction, not done here.

## What's deferred
Loading the FAISS index/parents once at startup instead of per-request (see above). Authentication/API keys — this endpoint has none at all, fine for local `uvicorn` testing, a real gap before it's reachable beyond localhost. Rate limiting and request logging/observability — this is exactly where `topics-glossary.md`'s Observability & tracing entry would actually get wired in, not done yet. Finer-grained error classification (transient outage vs. config/setup error) — see above. Real AWS deployment (API Gateway + Lambda, ECS, etc.) — this is a local `uvicorn` server only; deployment is a separate, later decision, same as the still-open S3 Vectors vs. OpenSearch Serverless choice in `vector-store-strategies.md`.

## Verification
Ran for real (Sept 16) — `uvicorn step06_api:app --reload` locally, then `Invoke-RestMethod -Uri http://127.0.0.1:8000/ask -Method Post -ContentType "application/json" -Body '{"query": "how do I clean up branches and stashes"}'` from PowerShell.

**Real result — a genuinely good demonstration of partial-coverage handling, distinct from the earlier full-refusal case**: only one weak match came back again (`note4-many-small.md`, relevance 0.0375 — same low-relevance match as the CLI run in `generation-strategies.md`'s Verification section, confirming HyDE still wasn't active in this PowerShell session either), but this time the sources partially covered the question — branch deletion (`git branch -d`/`-D`) and stash removal via `git stash pop` are both in the matched chunk. Rather than either fully refusing (the earlier case, where the match didn't cover the question at all) or fabricating a general "stash cleanup" command the sources don't contain, the model answered what the sources actually support, cited `[1]` correctly for both claims, and explicitly flagged the gap in its own answer ("the sources don't provide a command to directly delete or clear stashes"). This is the grounding behavior working exactly as designed at a *partial*-coverage boundary, not just the two easy extremes (clean hit / total miss) already seen.

**This also confirms `eu.anthropic.claude-haiku-4-5-20251001-v1:0` genuinely works end-to-end** — the flagged risk (cross-region inference profile IAM access not yet confirmed, see `step05_generate.py`/`query_transform.py`) did not materialize; the call succeeded with no `AccessDenied`/`ValidationException`.

`pytest tests\test_api.py` was reported as passing, but I don't have real pasted pytest output for this file specifically (only the `/ask` result above and a verbal "tested and committed") — consistent with this project's evidence-over-assertion habit, this isn't logged as verified until the actual test run output is pasted.
