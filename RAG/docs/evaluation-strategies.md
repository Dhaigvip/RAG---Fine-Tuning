# Evaluation Strategies — Reference

## Problem statement
Every change made to this pipeline so far — chunk size, hybrid fusion, reranker choice, the relevance threshold, parent/child promotion, HyDE — was judged by running one or two manual test queries and eyeballing the output. That's how the reranking threshold and the parent/child promotion-ordering bug were both actually found, so manual spot-checks have real value — but they don't scale and they don't catch regressions. Nothing currently stops a future change (a different chunk size, a different reranker model, a different `CANDIDATE_POOL`) from silently making retrieval *worse* for queries that aren't the one or two being manually tested at the time. "I think that helped" is a guess without a number to check it against — this is exactly what `rag-best-practices-checklist.md` section 8 calls out as "the step everyone skips."

## Correction to the original plan, before designing the solution
The Sept 14 plan entry says "score with RAGAS or a custom faithfulness/relevance rubric." Faithfulness and answer relevancy are **generation-quality metrics** — RAGAS's own docs confirm both require an actual generated `response` as input (faithfulness decomposes the answer into claims and checks each against retrieved context; answer relevancy compares the answer back against the question). This project has no generation step yet — Sept 15–16 is still ahead on the plan, and `step04_hybrid_search.py` only returns retrieved parent chunks, never a synthesized answer.

So faithfulness/answer relevancy literally cannot be computed against anything real right now — there's no answer to check for hallucination against. What's actually buildable today is a **retrieval evaluation harness**: a labeled question set with a known-correct source per question, run against `step04_hybrid_search.py`'s `search()`, scored on whether and where the correct source came back. This maps directly onto RAGAS's own retrieval-side metrics (context precision/recall) and the checklist's explicit call to "separate retrieval metrics from generation metrics." The generation-side metrics are deferred to Sept 15–16, once there's an actual answer to evaluate.

## Solution
Build a small, real, hand-labeled eval set from the existing 5-note test corpus (question → expected source file, optionally narrowed to a header for files with multiple sections), run it against `search()`, and score with retrieval metrics that don't require an LLM judge: Hit Rate and Mean Reciprocal Rank (MRR). Re-run this same eval set after every future retrieval-affecting change (chunk size, `CANDIDATE_POOL`, reranker model/backend, HyDE on/off) as a real regression check instead of a manual spot-check.

## Landscape of evaluation approaches

**Custom hand-rolled harness — chosen (for retrieval, right now).** A plain Python script: a JSON eval set, a metrics module (hit rate, MRR — both pure functions, no LLM call, no external dependency beyond what's already installed), and a runner that calls `search()` per question and compares results. Full transparency over what's actually being measured and why (the same "understand the mechanism, don't just call an API" approach used for hybrid fusion, promotion, and HyDE so far), zero new dependencies, and it reuses `search()`, `load_parents()` exactly as they already exist.

**RAGAS — the industry-standard framework, deferred (revisit once generation exists).** Widely recognized name (real interview value — Q4 in `interview-questions.md`, "evaluating LLM outputs," should reference it by name), provides both LLM-judged and non-LLM retrieval metrics (context precision/recall, the latter using string-similarity against reference contexts, no LLM required) plus the generation-side metrics this project will need at Sept 15–16 (faithfulness, response relevancy). The real cost: RAGAS's documented Bedrock integration path goes through `langchain-aws`'s `ChatBedrock` wrapper (`pip install ragas langchain-aws boto3 ...`) — this project has deliberately stayed on raw `boto3` everywhere (embeddings, HyDE generation) specifically to avoid extra dependency/IAM surface, the same reasoning that picked a directly-invocable Claude model over one needing a cross-region inference profile. Pulling in LangChain now, just to wrap a judge LLM call this project already knows how to make directly (see `query_transform.py`'s `generate_hyde_document()`), doesn't pay for itself yet. **Revisit at Sept 15–16**: once there's a real generation step, decide then whether RAGAS's packaged faithfulness/relevancy metrics are worth the dependency, or whether to hand-roll those too using the same Bedrock-judge pattern already established.

**DeepEval — considered, deferred.** Pytest-native (`assert_test`, `@pytest.mark.parametrize` over eval cases) — genuinely appealing given this project already has a `pytest` suite, and it would fold evaluation into `pytest` output alongside the existing 14 unit tests. Same dependency-footprint concern as RAGAS (its own LLM-judge wrapper, its own package), and pytest-style pass/fail assertions are a slightly awkward fit for what's wanted right now, which is a *score* (hit rate, MRR) to track over time, not a binary pass/fail per query. Worth reconsidering once faithfulness/relevancy need an LLM judge (Sept 15–16) if the pytest integration turns out to matter more then.

**TruLens — considered, declined for now.** Strong on production *observability* (tracing, dashboards, feedback functions over live traffic) more than one-off offline eval runs — a better fit once this project has a running FastAPI endpoint (Sept 15–16) generating live queries to actually observe, not for scoring a fixed labeled set today.

## Chosen design (retrieval eval, this step)
- **Eval set**: `RAG\eval\retrieval_eval_set.json` — hand-written, one entry per question: `query`, `expected_source_file`, optional `expected_header_contains` (a substring match against the promoted parent's `header_path`, needed because some notes — `note2-nested.md` in particular — contain multiple distinct parent chunks, so "the right file" alone isn't precise enough), and a `difficulty` tag (`exact` | `paraphrase`) so results can be broken down by how far the query's wording drifts from the source, the same axis that motivated HyDE.
- **"Parent" is not "whole document" — verified against real output, not assumed.** `step01_chunking.py`'s sibling-merge only combines sections sharing the same header depth AND fitting under the token budget together — it's per-section-group, not per-file. Checked the real `output/chunks.jsonl` (= `PARENTS_PATH`) directly to confirm every `expected_header_contains` value in the eval set is a real substring, not a guess: `note1-flat.md`, `note4-many-small.md`, `note5-no-headers.md` each happen to produce exactly one parent (small enough that everything merges), so file-level matching alone (`expected_header_contains: null`) is correct for those. `note2-nested.md` produces TWO distinct parents — `Load Balancing > Layer 4 vs Layer 7` never merges (it has no sibling under Load Balancing), while `Caching Strategies`'s two H3 children (Cache-Aside, Write-Through) do merge with each other — which is exactly why those two eval questions need `expected_header_contains` to disambiguate. `note3-lists-code.md` merges all three of its sections into one parent, but the merged `header_path` keeps every section name, comma-joined (`"... > Virtual Environments, Build Tools, Dependency Management"`), so `expected_header_contains: "Dependency Management"` still matches correctly even though it's merged alongside the other two sections in one physical chunk.
- **Metrics — Hit Rate and MRR, no LLM judge needed**: for each question, run `search(query, verbose=False)`, get back the promoted `(parent_id, score)` list, resolve each `parent_id` to its `source_file`/`header_path` via the existing `load_parents()`, and check whether the expected source appears anywhere in that list and at what rank.
  - **Hit Rate@k** = fraction of questions where the expected source appears anywhere in the `FINAL_TOP_K` results. Simple, interpretable, matches what actually reaches a user ("was the right thing anywhere in what came back").
  - **MRR (Mean Reciprocal Rank)** = mean of `1/rank` of the expected source across all questions (0 if absent). More sensitive than Hit Rate to *position* — a correct match at rank 1 scores very differently from the same file barely making it in at rank 3, which Hit Rate alone would treat identically.
  - This is exactly RAGAS's non-LLM context-precision/recall idea (compare retrieved results against a known-correct reference by identity, not by asking an LLM to judge relevance) — same methodology, hand-implemented, zero new dependency.
- **`search()` gets one additive change**: it currently only prints and returns nothing. Adding `verbose: bool = True` (default preserves all existing printed output and CLI behavior unchanged) and a `return promoted` (or `return []` when nothing passes the threshold) — this is the only code change to existing files; everything else is new files.
- **Re-run policy**: this eval set is meant to be re-run — not just after HyDE, but after *any* future change to `CANDIDATE_POOL`, `FINAL_TOP_K`, the rerank model, `LOCAL_MIN_SCORE`, or chunk size — exactly the checklist's "re-run after every pipeline change" item. Results are saved (not just printed) to `RAG\eval\results\` per run for that comparison.

## Query embedding cache (added Sept 14, after the first real eval run)
**Problem**: a fixed embedding call is technically deterministic (same input text → same Titan vector, always), but with HyDE on — the default — the *input* to that embedding call isn't the raw query at all, it's a freshly LLM-generated hypothetical passage, and generation is not deterministic. So even though `evaluate_retrieval.py`'s question set is literally the same 11 strings every run, re-running it re-triggers a real Claude Haiku call AND a real Titan Embed call per question, every time — including for pipeline changes (`CANDIDATE_POOL`, the reranker, `LOCAL_MIN_SCORE`, chunk size) that don't touch query embedding at all. Beyond the wasted cost/latency, this is a genuine confound: a Hit Rate/MRR shift between two eval runs meant to isolate one change could just as easily be HyDE phrasing things differently that time, not the change under test.
**Solution**: `query_cache.py` — cache the final embedding vector per query, keyed on the query text plus everything that can change what that vector is (transform mode, embed model id, and the HyDE model id when relevant). `step04_hybrid_search.py`'s `vector_rank()`/`search()` take an optional `cache` dict (default `None`, so the interactive CLI path is completely unaffected and still gets HyDE's real variation on every call); `evaluate_retrieval.py` is the one caller that opts in, since repeated fixed queries are exactly the case this solves. Stored as a plain JSON file (`eval/query_embedding_cache.json`) — delete it by hand to force a full re-embed (needed after changing HyDE's prompt template, which isn't part of the cache key).

## What's deferred
Faithfulness and answer relevancy (generation-quality metrics) — no generation step exists yet; revisit at Sept 15–16 once there's a real answer to score, and decide then whether to adopt RAGAS/DeepEval for that specific piece or continue the hand-rolled Bedrock-judge pattern. Context precision/recall in RAGAS's *LLM-based* form (comparing retrieved contexts against a reference answer via an LLM judge, as opposed to the non-LLM reference-contexts form this design already covers) — deferred for the same reason: no generated answer to use as the comparison anchor yet, and the non-LLM version already gives a real, if slightly less nuanced, signal today. Metadata-filtered retrieval evaluation (date/doc-type filters) — no such metadata exists in this test corpus yet (checklist item, still open). RAGAS/DeepEval/TruLens themselves are not rejected outright — each is named above with the specific reason it doesn't pay for itself at this exact step; worth reopening this decision once generation exists.

## Verification
Ran for real (Sept 14) — `python evaluate_retrieval.py` against the live Bedrock/FAISS pipeline (HyDE on, the current default), all 11 questions in `retrieval_eval_set.json`, results saved to `eval/results/20260914T144830Z.json`.

**Overall: Hit Rate 0.909, MRR 0.909 (10/11).**
- **`exact` queries: 6/6 — Hit Rate 1.000, MRR 1.000.** Every near-exact-wording query found its correct source at rank 1, no exceptions.
- **`paraphrase` queries: 4/5 — Hit Rate 0.800, MRR 0.800.** One miss: `docker-02` ("Why doesn't my container pick up changes after I edit the Dockerfile?", expecting `note1-flat.md`'s build-cache gotcha). Notably, this ran with HyDE active — the `[HyDE]` debug line printed a real, on-topic hypothetical passage ("Container Not Picking Up Dockerfile Changes... rebuild the container image...") — and it still missed. Every other `paraphrase` question hit at rank 1, including the original motivating case (`git-stash-01`, "how do I clean up branches and stashes").

**This is the first real, reproducible evidence of a genuine retrieval gap surviving HyDE**, not just a corpus-too-small null result like the single-query test earlier in this doc's history. Worth digging into eventually (is it a BM25/vector candidate-pool issue, a reranker threshold issue, or the HyDE passage itself pulling toward the wrong wording?) but not urgent at 11-question, 5-note scale — one miss out of five paraphrase questions is a single data point, not yet a pattern. Revisit once the eval set grows against real personal notes, where a repeatable miss on this same axis would be a much stronger signal.

**Interpretation of the whole run**: exact-keyword retrieval is solid at 100%; paraphrased retrieval is meaningfully weaker (80%) even with every mitigation in place (hybrid search, reranking, parent/child promotion, HyDE) — consistent with this project's original motivating observation (the `"git tag"` vs `"how do I clean up branches and stashes"` score gap) that paraphrase is the harder case, just not fully solved by any single technique alone.
